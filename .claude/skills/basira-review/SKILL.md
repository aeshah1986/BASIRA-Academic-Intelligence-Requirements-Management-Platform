# مهارة مراجعة «بصيرة»

## متى تُستخدم
- قبل حفظ أي مرحلة في Git، أو قبل التسليم.
- عند طلب «راجع المشروع»، أو «هل كل شيء يعمل؟»، أو «جهّز تقرير التحقق».
- **لا** تُستخدم لإضافة ميزات أو تعديل البيانات، فهي تقرأ وتشغّل الفحوص فقط، ولا تعدّل كود المنصة.

## الخطوات (بالترتيب، من مجلد `BASIRA/`)
1. `git status --short`. سجّل الملفات غير المحفوظة، ولا تحفظ شيئًا.
2. `node --test`. سجّل عدد الناجح والفاشل.
3. `node tests/e2e/browser-check.js`. يحتاج Edge أو Chrome، ويستغرق نحو 3 دقائق.
4. `node tests/report/build-report.js`. يعيد الخطوتين 2 و3 على نسخة نظيفة باتباع README، ويحدّث `TEST_REPORT.md`.
5. اقرأ `TEST_REPORT.md` §2 و§4، واستخرج:
   - كل حالة **فاشل** أو **لم يُختبر**.
   - حالات MUST **غير المنفذة**.
6. افحص الخصوصية بالأمر التالي، والمتوقع: لا نتائج (المسموح في الكود: `example.org` وعناوين وهمية في الفحوص فقط):
   ```bash
   git grep -nE "[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\.[a-z]{2,}"
   ```
   وتأكد أن `tests/demo-data.test.js` ناجح، فهو يفحص غياب الأسماء والأرقام الحقيقية.
7. اكتب التقرير بالقالب أدناه في `docs/reviews/review-YYYY-MM-DD.md`.

## قالب المخرج (إلزامي)
```markdown
# مراجعة بصيرة — YYYY-MM-DD
| # | الحالة | المتوقع | الفعلي | الدليل |
|---|---|---|---|---|
| 1 | الفحوص الآلية | 0 فاشل | … | مخرج node --test |
| 2 | فحص المتصفح | 0 فاشل | … | مخرج browser-check.js |
| 3 | اتباع README على نسخة نظيفة | R-01..03 ناجحة | … | TEST_REPORT.md §6 |
| 4 | حالات القبول | لا «فاشل» ولا «لم يُختبر» دون سبب | … | TEST_REPORT.md §2 |
| 5 | الخصوصية | لا بريد ولا بيانات حقيقية | … | git grep + demo-data.test.js |
| 6 | ملفات غير محفوظة | لا شيء قبل التسليم | … | git status |

## ما لم أستطع فحصه
- … (مثل: Firefox أو Safari، وقارئ الشاشة، والطباعة الورقية، وExcel)

## الحكم
جاهز / غير جاهز، مع السبب في سطر واحد.
```

## قواعد
- لا تكتب «ناجح» دون مخرج فعلي من هذا التشغيل. إذا تعذر فحص (لا متصفح مثلًا) فاكتب «لم يُنفذ» وسببه.
- انقل الأرقام من المخرجات كما هي، ولا تقرّبها ولا تجمّلها.
- الحالة غير المنفذة ليست ناجحة ولا فاشلة: اذكرها في سطر مستقل.
